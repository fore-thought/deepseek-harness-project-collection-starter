# units（单元文件夹）· 传送带

> 多角色流水线的核心不是"禁止并行"，而是**让每个文件只有一个写者**——于是并发不需要被禁止。
> 本文件说明约定；角色表与越界规程见组级 `../shared-standards/pipeline-and-roles.md`（路径相对项目根）。

## 一个单元 = 一个文件夹

```
units/u3-支付重试/
  brief.md          # 制作人写：做什么、验收细则、预期触碰的文件集
  build.md          # 实现者写：本单元施工记录（汇总）
  build-part1.md    # 实现者的子代理写（同前缀不同后缀）
  build-part2.md
  accept.md         # 验收员写：逐条打勾的验收报告
```

- **文件夹由第一个写它的人懒创建**，不需要预先建目录。
- **每份文件只有一个角色写**：`brief.md` 永远属于制作人，`build*.md` 永远属于实现者，
  `accept.md` 永远属于验收员。归属是路径的属性，不是比出来的。
- 格式参考 `../../templates/units/` 下的三份模板。

## 四条容易踩的约定

1. **`brief.md` 交出后不再改**。要改就出 `brief-v2.md` 或追加 `brief.addendum.md`——
   否则实现者会基于过期视图施工。
2. **同角色的并发会话与子代理**：都写 `build.md` 会撞车。各写 `build-part<N>.md`，
   再由该角色的下一次交接汇总进 `build.md`。
3. **实现者的施工记录里留一节「候选决策与候选假设」**：让"想记录"的冲动有正当出口，
   不必去写制作人的共享日志（新数字也先写这里，由制作人登记进 `assumptions.md`）。
   由制作人判断哪些升格成 ADR、哪些升格成假设条目。
4. **命令产生的临时文件一律进 `process/tmp/`**：跑构建、测试、脚本都不该在别人命名空间里
   留下文件——"命令产文件"等同于"你写文件"（组级 `pipeline-and-roles.md` §3.1 第二档）。

## 单会话模式

不用角色时，一个会话可以自己把三份文件都写完（或只写 `build.md` + `accept.md`）。
本目录的约定不变，只是写者变成同一个会话。
