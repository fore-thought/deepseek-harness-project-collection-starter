# 工作原则与协作规范（AGENTS·项目组级）

> 本文件 = **项目组级公共规范**：位于 `project-group/shared-standards/`，被项目组内
> 各项目工作区**只读引用**（不随项目复制）。**开始任何任务前先读本文件。**
> 变更需用户确认；更新走提权通道（见 §8/§9）。
> 版本: v1.0 ｜ 最近修订: 2026-08-27 ｜ 变更记录见文末。

## TOP 规则（最高优先级，与其他内容冲突时以本块为准）

1. 未签目标书不立项；未批计划书不执行。
2. 一个单元=一个分支=一个会话；收单元七步打勾缺一不可。
3. 请示用户一律用提问卡片。
4. 闸没过完禁止进入下一单元。
5. 里程碑完成第一时间总结+推送到远端仓库。

## 0. 协作模式（用户-代理）

- **用户**：负责战略方向与重点细节抉择；提供账号注册与权限管理；
  有权驳回请求并给出指引。
- **代理**：负责执行与落地；工作区维护；遵守领域互联网工程规范。
- **工作流程**（每项任务必须走完）：
  1. 先向用户了解工作内容与方向（不臆测，先问）；
  2. 写出详细计划书：待执行步骤 + 验收标准；
  3. 严格执行，**不主动降级任务目标**；
  4. 完成后验收并向用户汇报。
- **被驳回时**：不辩解硬闯，思考备用方案再提出；用户有思路时遵从用户指引。
- **咨询方式**：咨询/请示用户时**优先使用提问卡片**（ask_user_question，带选项，
  推荐项标注），便于快速回复；复杂情况卡片 + 简要文字结合。
- **规范沉淀**：每次遇到"规则冲突/无规范可循"的情况，先查可查到的领域规范或
  咨询用户，然后归纳总结、把结论写入本文档或项目级 AGENTS/standards，形成积累。

## 1. 项目组定位

- 项目组：`<一句话项目组定位（例：AI 动画二创项目组）>`
- 成员项目：每个项目 = 一个**独立工作区**（与 shared-standards 同级的文件夹，
  由 `project-template` 复制改名而来，在 DSH 中单独打开）。
- 项目工作区按**三大类**组织：`inputs/`（输入素材）、`process/`（过程工程）、
  `outputs/`（输出产物），根级文档只有 AGENTS.md（三类索引见项目级 AGENTS §3）。
- 各项目 `inputs/ai/reports/` 下调研报告 = **市场调研 + 可行性分析**，不是工程方案，
  不是事实来源。

## 2. 核心工作原则

1. **怀疑态度**：报告中的每个数字都当成"待验证假设"，引用时必须标注假设 ID
   （见项目 `process/docs/assumptions.md`），不得直接作为事实写进方案。
2. **先问人，再搜网**：遇到无法判断或互相矛盾的信息，先问用户；用户不能准确回答时，
   上网搜索核实并附来源链接。
3. **实测优先**：涉及本机能力的结论，必须以真机实测为准；纸面估算只能作为预测，
   并在文档中标注 [ESTIMATED]。
4. **结论分层（强制范围）**：凡文档中出现数字、阈值、事实性结论，必须标注
   [MEASURED] 实测 / [ESTIMATED] 估算 / [UNKNOWN] 未知待定；涉及外部信息同时挂
   [ASSUMPTION-XXX]；纯流程/导航性描述不强制。
5. **定价敏感**：所有价格类信息随时变动，立项前必须重新询价；促销价不代表稳态价格。
   **询价只看官方渠道**（官网定价页/官方文档/官方客服）；第三方评测、自媒体文章、
   AI 生成内容一律不作定价与选型依据。

## 3. 已知不可靠内容（各项目登记见各自 process/docs/assumptions.md）

- 第三方价格评测、自媒体价格文章、AI 生成的价格/规格描述——不作定价与选型依据，以官方为准。
- `<项目组级已知不可靠内容，逐条列出>`

## 4. DSH 友好约定（工程协作格式）

- 所有文档：UTF-8（无 BOM）、Markdown、LF 换行。
- 文件名：小写字母 + 连字符（如 `working-principles.md`），不使用空格和中文文件名。
- 行宽：正文每行 ≤ 100 字符（表格除外），方便逐行读取。
- 标记约定（可 grep 检索）：
  - `[ASSUMPTION-XXX]` —— 引用项目 `process/docs/assumptions.md` 中的假设编号
  - `[TODO]` —— 待办
  - `[VERIFY]` —— 待核实（上网或问人）
  - `[MEASURED]` / `[ESTIMATED]` / `[UNKNOWN]` —— 结论类型
  - `[SOURCE?]` —— 缺来源
- 文件引用一律用相对路径。
- 修改现有文件前先 read；新增文件用 write；小改动用 edit。
- 不要生成超长单行；大文档按小节组织，便于 grep 定位。

## 6. 通用工作规则与项目组特色定制

**通用：**
- 启动工程方案前：先过一遍项目 `process/docs/assumptions.md`，标出会影响方案的关键假设。
- **假设登记义务（A1）**：任何新调研/新数字产出时，**先登记假设，再引用**；调研报告交付的
  同时更新 `process/docs/assumptions.md`——登记条目 = 调研收尾凭证，未登记 = 报告不算交付完成。
- **验证时机分层（A1b）**：假设登记时标注 `验证时机`：近期可实测 / 上线后验证 / 仅参考；
  "上线后验证"类在里程碑复盘统一到期检查，到期未验证的补验证或降级为"仅参考"。
- **决策记录（A2）**：命中下列任一即当天记 ADR 到 `process/docs/decisions.md`
  （与 work-log 同节奏），状态机：提议 → 已批准/已驳回/已废弃：
  ①方向/边界/排除项变化；②指标口径或成功判定变化；③成本上限/预算哲学变化；
  ④技术选型变更；⑤平台集合/渠道变更；⑥影响 ≥2 个单元或跨里程碑。
- **新会话接续**：先读项目 `process/docs/HANDOFF.md` + `process/docs/work-log.md`，
  再开始工作；重大决策记入项目 `process/docs/decisions.md`。

**项目组特色定制（全局适用，各项目默认遵守）：**
- **大文件下载规范**：凡需从外网下载大文件（模型权重等），一律由用户在主机执行下载
  （代理沙箱对大文件下载不可靠）。代理负责列出**下载表格**，每行至少含：
  `下载网址` + `下载后存储位置`（完整路径）。下载完成后用户告知，代理再继续。
- **选型规范**：一律选主流成熟方案，不选冷门小众的；除非双方共同确认现有效果不好，
  再由用户决定是否更换。自训微调产物除外。
- **提交习惯**：里程碑式成果或反复修改最终成功的大成果，第一时间总结
  （写进 work-log/decisions + 必要时施工文档），然后**提交 git = 推送到远端仓库**，
  不止本地 commit。真有问题再回滚或 fork 新分支。
- **资源约束**：本机资源紧张的任务不并行（以实测资源占用为准；冲突时由用户排定先后）。
- **施工文档约定**：交付版施工文档 `process/docs/construction.md` 只记录**成功实施步骤**
  （错改对的一步到位），使**换 AI/换工作目录也能从空文件夹复原当前项目进度**。
  ⚠️ 它与 **`process/docs/work-log.md`（每日实际施工日志，全路径，含反复修改/失败）是两份**，勿混。
- **重复动作脚本化**：同一动作第二次出现（人工/纸面重复操作、需复现的步骤），即落地为
  可执行脚本，放项目 `process/project/scripts/`，随 git 版本化。脚本须**可观测**：明确的
  入参/出参、日志输出、非零退出码标识失败。**日志分级**：
  - 关键结点（成功路径）：阶段转换、入参摘要、中间结果——详细记录，不一句带过；
    后续若出现错误，之前的关键成功日志是排错推理的重要依据；
  - 常规过程（成功路径）：简洁，不刷屏，不堆 debug 打印；
  - 错误路径：详尽——错误信息、触发上下文、当时输入状态，以"拿到日志就能排错"为目标。
  目的：减少模型重复推理、节约 token 用量、保证结果一致可复现；收单元验收时可用脚本
  复现替代口头描述。
- **成本治理**：成本账目记 `measurements.md`（实测）+ `work-log.md`（每单元一行），
  不另开文档；预算总额在计划书（规划闸）确定；超预算 → 停止 + 卡片请示，不自动放行；
  询价结论先登记假设（状态=待询价），实测后转 [MEASURED]。
- **git 双模式**：远端模式（默认推荐：commit + push）与本地模式（用户明确选择：
  仅本地 git，commit 即收尾）均合法，模式记入项目 HANDOFF。**每次 git 操作前**
  先查 `git remote -v` 并向用户说明三问：①是否已设置远端？②是否仅提交本地？
  ③是否已推送远端？——防止"以为推了其实没推"。
- **里程碑复盘（D3）**：每里程碑（一轮 30 条优化闭环/单元组收完/用户指定）强制复盘：
  ①成功判定逐条打勾；②规约执行偏差清单（未遵守/写不清/执行不了）；
  ③偏差 → 修订提案（走 §9 D1 流程）；④纪要入 decisions + work-log；
  同时执行"上线后验证"假设的到期检查。
- **规则预算（新增规约的过滤器）**：新规则提案须附"防什么事故"说明（频率×损失）；
  无法说明具体事故的不采纳或降为建议。TOP 规则与四道闸为锚点，不参与筛选。

## 7. 门禁执行规范（四道闸·可执行版）

> 目的：门禁靠物理动作执行，不靠自觉。每条含"触发条件/具体动作/通过凭证/失败默认动作"。

### 7.1 立项闸（新项目会话第一步，做完才能做别的）

1. 写项目 `process/docs/plans/goal-spec.md`，固定 6 个必填字段（缺字段不算写完）：
   - `成品形态`：一句话 + 一段让没参与的人能看懂最终成品长什么样的描述
   - `质量上限`：标杆是谁（贴具体链接/图，不许写"高质量"这类形容词）
   - `质量下限`：什么样的结果不可接受（具体到画面/时长/观感）
   - `渠道与受众`
   - `成功判定`：列 3 条事后能打勾的指标
   - `排除项`：明确不做的事
   - 字段可以"**原则级 + [VERIFY] 占位**"签署（方向承诺与细节充实解耦），细节由调研阶段回填。
2. 用提问卡片把 6 字段逐一请用户确认，用户答"通过"=签名。
3. 未签名 → 禁止执行任何后续动作（含调研）。

**目标书修订分级**：
- **字段级变更**（成品形态/渠道与受众/排除项/成功判定结构等）→ 需回到本闸**重新签名**；
- **细节充实**（指标字典版本升级、阈值校准等）→ 用户确认 + 记入 decisions/work-log，
  不必重签。

### 7.2 规划闸（目标签名后）

1. 请用户开 /plan 模式；写计划书并附门禁表（每行固定 4 列：
   `触发条件 | 通过凭证 | 通过后做什么 | 未通过默认动作（停止+卡片请示）`），
   用 exit_plan_mode 提交计划。
   **格式定义与示例在同一小节、同一版本块**（示例不同步更新的修订不予批准）。
   示例行：
   | 触发条件 | 通过凭证 | 通过后做什么 | 未通过默认动作 |
   |---|---|---|---|
   | 单元 U1 验收 | 门禁逐条打勾 + 成果入 work-log/construction + commit/push + 用户确认"通过" | 进入 U2 | 停止 + 卡片请示（修改或重做） |
2. 计划书批准 = 用户在 /plan 里点批准；未批准禁止执行。

**决策↔计划书联动（A2b）**：
- 执行中决策：仅"影响验收标准/门禁表/指标口径"的决策须**当天同步计划书对应行**
  （1 行编辑）；背景方向类决策只记 ADR；
- **里程碑收尾全量回写（A 操作）**：该里程碑期间全部决策（含背景类）统一落进
  计划书/门禁表，保证 decisions ↔ 计划书完全对齐；顺序：①决策回写 → ②里程碑复盘 →
  ③总结+推送（TOP 规则 5）。

### 7.3 执行闸（每个工作单元循环）

- 工作单元定义写在计划书里，格式固定："一个可验收产出"
  （例：一个模型训练完成并通过验证）。
- **单元命名**：`u<序号>-<kebab-case 主题>`（小写+连字符），如 `u1-platform-observability`；
  分支 = 单元名；会话名 = `<单元名>-<YYYYMMDD>`。
- 开单元：`git checkout -b <单元名>` + 新开会话，会话名=`<单元名>-<日期>`。
- 收单元七步（逐条打勾，缺一不进入下一单元）：
  1. [ ] 对照计划书门禁表逐条验收打勾
  2. [ ] 成果写入 process/docs/work-log.md（表格一行）
  3. [ ] 成功步骤写入 process/docs/construction.md
  4. [ ] `git commit`（信息规范见下）
  5. [ ] `git push origin <分支名>`（远端模式；本地模式仅 commit，模式记入 HANDOFF）
  6. [ ] 提问卡片问"单元 X 验收通过？[通过/修改]"，用户通过才收
  7. [ ] 提议切新会话（见"切会话分工"）
- **commit 信息规范**（Conventional Commits 结构）：
  - 首行：`<type>(<单元名>): <一句话成果>`，如
    `feat(u1-platform-observability): 7平台可观测性核实+指标字典v1.1`
  - type 固定集：`feat`（新成果）/ `fix`（修复）/ `docs`（文档）/ `refactor`（重构）/
    `test`（测试）/ `chore`（杂务/脚本/配置）
  - body：单元收尾类提交**必写**（验收要点、关联 DECISION/ASSUMPTION 编号）；
    简单 chore 可省略
  - footer：GitHub 联动（`Fixes/Closes #N`）可选
- **上下文检查**：每个收尾检查点（单元收完/里程碑/长会话中途）运行上下文占用查询脚本
  （项目 `process/project/scripts/ctx.cjs`，读 DSH 会话日志），占用 ≥60% → 走切会话收尾流程。
- **切会话分工**：
  - 代理（收尾方）：停手 → 更新 HANDOFF/work-log/decisions → git 提交 → 卡片提议 +
    给出"**新会话第一句话**"（可复制文本）；
  - 用户（接续方）：新建会话窗口 → 发第一句话 → 新会话自动走接续闸。
- 强制切会话触发条件（任一命中即停手、卡片提议切会话）：
  - 一个单元收完；当日已完成 ≥2 个单元；上下文占用 ≥60%（代理自测或用户提醒）；
    用户说收工
- **等待用户确认期间**（收单元第 6 步、卡片请示）：
  - 允许做"非冲突工作"：不依赖该决策的独立准备（下一单元调研、文档整理、无冲突脚本化）；
    非冲突工作**有界**——完成一项可验收的独立准备即回到等待；无非冲突工作时停止，
    不制造无效工作（不为填时间硬找事做）；
  - **禁止**：开新单元、修改已提交内容、任何越闸动作（闸没过完不进下一单元）；
  - 跨会话无回复：用户收工/新会话开始时，HANDOFF 记"挂起事项 + 等待的决策点 +
    恢复路径"，下个会话从该点继续。

### 7.4 接续闸（新会话第一步，固定顺序）

1. 读 process/docs/HANDOFF.md → 2. 读 AGENTS.md TOP 规则 →
   3. 读 process/docs/work-log 尾 10 行 + process/docs/decisions 索引
   → 4. 判断当前处于哪道闸、过闸凭证是否齐全，不齐先补。

### 7.5 文件职责补充

- 项目 `process/docs/plans/goal-spec.md`：目标定义书（立项闸产物，
  6 字段模板见 §7.1），任何项目立项前必写。

### 7.6 调研阶段（可选，立项与规划之间）

> 不是第五道闸，是轻量阶段；目标书细节已明确、无需调研的项目可跳过直接进规划闸。

- 触发：目标书签名后、规划闸前；需要充实目标书细节或为计划书铺路时进入。
- 范围："信息收集"类——平台可观测性、标杆池、互动基线、成本询价、合规核实等；
- 边界：**禁止工程实现**（不写代码、不搭系统）；所有数字须登记假设（A1）
  并标注结论分层；
- 退出凭证：调研报告交付 + 假设登记完整 + 用户确认调研结论；
- 失败默认：停止 + 卡片请示（未知项转 [UNKNOWN]/[VERIFY]，或由用户提供）。
- 产出物：调研报告入 `inputs/ai/reports/`；结论按修订分级回填目标书；登记假设。

## 8. 依赖与更新规则（项目组级 ↔ 项目级）

- **引用**：各项目工作区的 `AGENTS.md` 第 0 节声明依赖本文件
  （相对路径 `../shared-standards/AGENTS.md`）。
- **新项目创建**：复制 `../project-template/` 到本文件夹同级（project-group 下）
  并改名，以**独立工作区**在 DSH 打开；`../shared-standards/` 相对路径自动成立。
- **只读**：本文件夹对各项目工作区只读（项目代理的写权限只覆盖本项目工作区）；
  项目不得把规范复制进工作区形成双份。
- **更新**：本文件夹规范由用户主导更新；代理需要更新时走**提权通道**——
  对越界写操作申请一次性权限并说明理由，经用户批准后执行。
- **优先级（两档制）**：
  - TOP 规则为最高优先级，**不可被项目覆盖**（动它们需用户主导）；
  - 其余组级条款为**默认值**：项目可覆盖，但须在项目级 AGENTS §2 显式写明覆盖条款
    与理由；覆盖若具通用性，走提权通道回写组级，不留隐性分叉。

## 9. 规约修订流程（D1）

> 规约自身的修改流程。入口：**反作用专用会话**——要分析/修改规约时，开一个专用会话
> （先读规约 → 分析完整性 → 讨论确认 → 按本流程落地）；日常干活会话不混入规约修改。

1. **提案**：修订动议。简单修订（单文件、文字级）会话内确认即可；复杂修订
   （跨文件、机制级、影响面大）写成文提案 = 现状问题 + 拟改条款原文 + 影响范围
   （组级/项目级/模板层），放项目 `process/docs/spec-proposals/`；
2. **批准**：用户确认。组级修订**必须用户明确批准**（代理只提案、不推动）；
   项目级修订用户确认即可；
3. **实施**：项目级 = 工作区内直接改；组级 = 提权通道改 shared-standards
   （+ 回写 starter 仓库，push 由管理员执行）；
4. **版本化**：被改文件版本号 +1（见文末变更记录）；
5. **变更记录**：记入文件内变更记录表；含示例的条款必须同步更新示例
   （作为批准环节校验项）。
